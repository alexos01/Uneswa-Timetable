UNESWA Timetable: system design

Turning the web timetable students already use into installable Android and iPhone apps. Class reminders fire even when the app is closed, and the app gains multi-campus admin, lecturers, class reps and announcements. The website itself installs from the browser, works offline and gets push notifications.

Repo: alexos01/Uneswa-TimetableBranch: mainDrafted 1 Oct 2026Live: alexos01.github.io/Uneswa-Timetable

Summary

The app stays one codebase. The same HTML, CSS and JavaScript serves the website on GitHub Pages and runs inside a Capacitor shell for Android and iOS. Supabase remains the only backend. The mobile shell adds what a browser tab can't do reliably: scheduled notifications, sharing a PDF to WhatsApp or Files, the Android back button, and opening offline with the last saved timetable.

Where it started

One file, index.html (about 1,560 lines), holds the whole app. It uses vanilla JavaScript that renders with template strings, supabase-js, jsPDF from a CDN, and an AI import panel that brings its own key for Anthropic, Gemini, OpenRouter or Ollama. GitHub Pages serves it straight from the root of main.

What limits it as a phone app

  • Reminders use setInterval plus the browser Notification API, so they only fire while the tab is open.
  • PDF export calls doc.save(), which does nothing inside an Android WebView.
  • Every realtime change reloads all 2,954 rows. A bulk import of 3,000 lines sets off thousands of full reloads.
  • Module search runs across every course, so students see modules from other streams.
  • There's one admin for everything, and no notion of campus, lecturer or announcement.

Architecture

One set of HTML, CSS and JavaScript runs in three places: the website on GitHub Pages, the Android app and the iPhone app. Supabase is the only backend. js/platform.js decides at runtime whether it is in a browser or the phone shell, so feature code never checks the platform itself.

Why there's no bundler

GitHub Pages serves main exactly as committed. The code is split into ES modules that the browser loads directly, with third-party libraries copied into vendor/, so the site keeps working on every push without a build step or Pages settings. Capacitor only needs a folder of static files, so npm run build copies the web files into www/ and npx cap sync carries them into both native projects. Native plugins are reached through registerPlugin() from the vendored @capacitor/core; on the web they are never called.

How it works

Opening the app

The app first sends anything left in the offline outbox, then asks the database what it supports and loads the student's campus. If the server can't be reached it opens on the copy kept on the device and says it is offline.

Working offline

  • The service worker serves the app files, so the site opens with no signal once it has been visited (or installed) once.
  • The whole campus timetable is on the device, so a student can browse courses and tick modules.
  • A save that can't reach the server goes into the outbox and the header shows how many changes are waiting. A save the server refuses still shows an error.
  • When the browser reports it is back online (or the phone app resumes), the outbox is sent first, then everything reloads, and the student sees "You're back online".

A class running late

sequenceDiagram
  participant L as Lecturer or class rep

  L->>DB: insert class_notice (kind late, 15 min)
  Note over DB: RLS: only for their assigned modules
  DB-->>B: realtime change (page open)
  B->>B: reload, show "Running 15 min late", notify now
  DB->>F: trigger on insert
  F->>F: find subscriptions following that module
  F-->>B: Web Push (page closed)
  DB-->>P: realtime change while the app is open
  P->>P: notify now, reschedule the reminder for the delayed start

Both the page and the push use the same notification tag (notice-<id>), so a student who gets both sees one notification.

Class reminders

  • Phone app: one repeating local notification per session at the chosen lead time (10 minutes by default), rescheduled whenever modules, notices or settings change. No server is involved.
  • Browser with push on: pg_cron calls send-push every minute; it sends each student the sessions starting their lead time from now, skipping cancelled classes and moving late ones.
  • Browser without push: reminders fire only while the page is open.

Uploading the official timetable

An admin uploads a CSV (from Excel or Google Sheets) under Class timetable or Exam timetable. js/lib/csv.js matches columns by name, tidies days, times and dates, and lists bad lines; nothing is written until the admin confirms. Rows already on the timetable are skipped, so importing twice adds nothing. A PDF goes through AI Import instead, where the admin reviews every proposed row.

Roles & access

Postgres row-level security enforces the rules, not the UI. Three security definer helpers, is_super_admin(), is_campus_admin(campus) and teaches(campus, code), keep the policies short. The migration drops every existing policy on the affected tables and recreates them, because the original policy names were never committed to the repo.

How staff get accounts

  1. The person opens Staff sign in → Create account in the app, which runs a Supabase Auth sign-up.
  2. Their campus admin enters the email under Admin → Staff and picks a role. The RPC grant_staff_role(email, role, campus) resolves the email to a user id on the server and checks that the caller is allowed to grant that role.
  3. For a lecturer or class rep, the admin then assigns module codes. Lecturers work under the Lecturer tab and reps under Class rep; signing in on any tab moves to the right one.

When the migration runs, every account in Authentication → Users becomes a super admin. Today that should only be the existing admin login, so check that list before running it.

Safe rollout

Pushes to main go live straight away for the students using the site, so the new code has to work against the database as it is now and as it will be after the migration.

  • At startup db.js probes for the campuses table. If it's missing, the app runs in single-campus mode: legacy settings row 1, any signed-in user is admin (as today), and no lecturer or announcement tabs. Admin shows a banner pointing to the migration file.
  • Migration 003 adds app_schema_version(). While it's missing, the Class rep tab, "running late" notices, course announcements and push stay hidden; everything else works.
  • Migrations are idempotent (if not exists, policies dropped before they're recreated), so running one twice is harmless.
  • Someone with Supabase dashboard access runs each file once in the SQL editor. The app can't do it, because it only holds the public anon key.

Native features

Class reminders that fire when the app is closed

  • @capacitor/local-notifications sets up one weekly repeating notification per class session, using schedule.on {weekday, hour, minute} and allowWhileIdle, at the student's chosen lead time (5 to 60 minutes).
  • Tests and one-off notices get a single notification the evening before at 18:00, plus one at the lead time.
  • Reminders are rescheduled whenever the module list, lead time, campus, notices or semester changes. Everything pending is cancelled first, so nothing piles up.
  • iOS keeps at most 64 pending notifications, so the scheduler caps at 60 and fills them in order of soonest first.
  • Android declares SCHEDULE_EXACT_ALARM and uses a "Class reminders" channel. Android 13+ asks for notification permission the first time a student turns reminders on.
  • A "running late" notice gets one reminder before the delayed start instead of the evening-before one.
  • While the app is open, a new late, cancelled or moved notice for one of the student's modules shows a notification as soon as it arrives over realtime.

Web app: install, offline and push

  • sw.js keeps every app file. Files come from the network first, so a deploy reaches students on their next visit, and from the copy when the network is slow (4 s) or gone. A unit test fails if a new file isn't in its list. An Install app button shows when the browser offers it.
  • The whole campus timetable is kept in IndexedDB after each load, so courses can be browsed and modules ticked with no connection. Student changes go to an outbox and are sent before anything else loads once the connection returns; the header shows how many are waiting.
  • With reminders on and push configured, the browser subscribes to Web Push and stores the subscription with the student's sessions and lead time. The send-push Edge Function sends a push when a class notice or announcement is posted (database trigger) and the class reminders due each minute (pg_cron), following any late, cancelled or moved notice for the day. Tags match the in-page alerts, so the same alert never shows twice.
  • On an iPhone, push needs the site added to the Home Screen first (iOS 16.4+).

PDF export

On native, the jsPDF output is written to the cache directory with @capacitor/filesystem and handed to the share sheet with @capacitor/share, so it can go to WhatsApp, Drive or Files. On the web it downloads as it does now.

Offline open

After each successful load, the campus timetable, notices and announcements are kept on the device (see Web app above; the phone app uses the same copy). With no connection, the app opens on that copy and shows an "offline, last updated …" note.

Shell polish

Android's back button returns to My Timetable before leaving the app. The status bar takes the brand colour, the splash screen hides after the first render, and icons and splash images come from @capacitor/assets.

Feature specs

Search fix

Search is limited to the student's campus. By default it searches only the chosen course, and a toggle widens it to "all courses on this campus" for electives. Each result shows its course name, and the same module code is never listed twice.

Multi-campus

Students pick a campus on the sign-in screen, and it's saved to their record. Admins see only their own campus, and the class, exam and AI import tabs write campus_id automatically. A super admin gets a campus switcher. Faculties and courses are per campus.

Lecturers tab

A lecturer signs in and sees only their assigned module codes. For each code they can move a session for good (day, time, venue), or post a one-off notice: test, cancelled, moved, extra class or note. Students see these notices next to the class in their timetable and in a "Coming up" list.

Class rep tab

A class rep is assigned module codes like a lecturer. They get the same notice form and session editor for those codes, plus a form to announce to the courses those codes are taught on, optionally to one year. Students see an announcement for a course only if they take a module on it (in that year).

Running late

Lecturers and reps can mark a class as running 5 to 60 minutes late. Late, cancelled and moved notices fill in the class's time and venue from the timetable, and the student's next-class banner shows any same-day change.

Official timetable in and out

Admins upload the class or exam timetable as CSV from Excel or Google Sheets. Columns are matched by name in any order, semicolon files and a Time range column are understood, and days, times and dates are tidied. The admin sees what will be imported and which lines are skipped before anything is written, and re-importing adds nothing. A template and the current entries download as CSV. Students can download any course's (and year's) official timetable as a PDF grid with its exams, or as CSV. A university PDF still goes through AI Import.

Announcements tab

Students get an Announcements tab with campus and all-campus posts, pinned first, and expired posts hidden. Admins can create, pin, set an expiry and delete.

Contact footer

A footer gives the maintainer's contact email for queries, plus LinkedIn and Facebook links. The links live in js/config.js, and each one is hidden until its URL is filled in.

Smaller fixes found during review

  • Realtime reloads are debounced so a bulk import causes a single reload.
  • Data loads are filtered by campus, so only that campus's rows are fetched.

Operations

Deploying

  • Pushing to main is the deploy: GitHub Pages republishes the site within a couple of minutes. Students get the new files on their next visit, because the service worker tries the network first.
  • CI (.github/workflows/mobile.yml) runs the unit, UI, database and function tests, then builds the Android APK and the iOS app. A failing test shows as an annotation on the run page.
  • To undo a bad deploy, git revert the commit and push. The site rolls back on the next Pages build.

Running a migration

  1. Open the Supabase dashboard, then SQL Editor → New query.
  2. Paste the whole file from supabase/migrations/ and click Run. Every file is safe to run again.
  3. Reload the site; the features switch on by themselves.

Only someone with dashboard access can do this; the app holds only the public anon key. Before 001, delete test accounts under Authentication → Users, because every account there becomes a super admin. Migrations only add tables, columns and rules, so rolling back means reverting app code, not the schema.

Turning on push for the website

Needs migration 003. Make a VAPID key pair, put the public key in js/config.js, set the secrets, deploy send-push with --no-verify-jwt, and run its setup.sql. The full steps, and how to turn it off again, are in supabase/functions/send-push/README.md. Edge Functions → send-push → Logs shows each call and how many messages were sent.

Each semester

  • Upload the new class and exam timetables as CSV (Staff → Class timetable / Exam timetable). Download CSV template gives the columns.
  • Start the new semester under Staff → Settings. Students' module lists are archived and cleared the next time they open the app.
  • Settings → Clean up duplicate entries shows any rows imported twice and removes the extras.

Staff accounts

The person creates an account under any sign-in tab (Create a staff account). A campus admin adds their email under Staff → Staff & lecturers, picks Lecturer or Class rep, and assigns module codes. Only a super admin can create admins.

Risks & open items

Student records are publicly readable and writable. Students sign in with a student number and no password, so anyone with the anon key can read or change any student's record. That's tolerable for module lists, but app-store privacy reviews will ask about it. A fix means real student sign-in, for example a magic link to the university email. It's outside this plan.
