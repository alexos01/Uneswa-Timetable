UNESWA Timetable for Android & iOS

Turning the web timetable students already use into installable Android and iPhone apps. Class reminders fire even when the app is closed, and the app gains multi-campus admin, lecturers and announcements.

Repo: alexos01/Uneswa-TimetableBranch: mainDrafted 1 Oct 2026

Summary

The app stays one codebase. The same HTML, CSS and JavaScript serves the website on GitHub Pages and runs inside a Capacitor shell for Android and iOS. Supabase remains the only backend. The mobile shell adds what a browser tab can't do reliably: scheduled notifications, sharing a PDF to WhatsApp or Files, the Android back button, and opening offline with the last saved timetable.

Where it started

One file, index.html (about 1,560 lines), holds the whole app. It uses vanilla JavaScript that renders with template strings, supabase-js, jsPDF from a CDN, and an AI import panel that brings its own key for Anthropic, Gemini, OpenRouter or Ollama. GitHub Pages serves it straight from the root of main.

What limits it as a phone app

  • Reminders use setInterval plus the browser Notification API, so they only fire while the tab is open.
  • PDF export calls doc.save(), which does nothing inside an Android WebView.
  • Every realtime change reloads all 2,954 rows. A bulk import of 3,000 lines sets off thousands of full reloads.
  • Module search runs across every course, so students see modules from other streams.
  • There's one admin for everything, and no notion of campus, lecturer or announcement.

Target architecture

The web build and both app builds load the same files. The shell decides at runtime which platform adapter to use, so feature code never checks the platform itself.

Why there's no bundler

GitHub Pages serves main exactly as committed. If the code were split into ES modules that the browser loads directly, with third-party libraries copied into vendor/, the site would keep working on every push without touching the Pages settings. Capacitor only needs a folder of static files, so npm run build copies the web files into www/ and npx cap sync carries them into both native projects. Native plugins are reached through window.Capacitor.Plugins, which Capacitor's native bridge injects, so no import step is needed either.

Roles & access

Postgres row-level security enforces the rules, not the UI. Three security definer helpers, is_super_admin(), is_campus_admin(campus) and teaches(campus, code), keep the policies short. The migration drops every existing policy on the affected tables and recreates them, because the original policy names were never committed to the repo.

How staff get accounts

  1. The person opens Staff sign in → Create account in the app, which runs a Supabase Auth sign-up.
  2. Their campus admin enters the email under Admin → Staff and picks a role. The RPC grant_staff_role(email, role, campus) resolves the email to a user id on the server and checks that the caller is allowed to grant that role.
  3. For a lecturer, the admin then assigns module codes.

When the migration runs, every account in Authentication → Users becomes a super admin. Today that should only be the existing admin login, so check that list before running it.

Safe rollout

Pushes to main go live straight away for the students using the site, so the new code has to work against the database as it is now and as it will be after the migration.

  • At startup db.js probes for the campuses table. If it's missing, the app runs in single-campus mode: legacy settings row 1, any signed-in user is admin (as today), and no lecturer or announcement tabs. Admin shows a banner pointing to the migration file.
  • Migrations are idempotent (if not exists, policies dropped before they're recreated), so running one twice is harmless.
  • Someone with Supabase dashboard access runs each file once in the SQL editor. The app can't do it, because it only holds the public anon key.

Native features

Class reminders that fire when the app is closed

  • @capacitor/local-notifications sets up one weekly repeating notification per class session, using schedule.on {weekday, hour, minute} and allowWhileIdle, at the student's chosen lead time (5 to 60 minutes).
  • Tests and one-off notices get a single notification the evening before at 18:00, plus one at the lead time.
  • Reminders are rescheduled whenever the module list, lead time, campus, notices or semester changes. Everything pending is cancelled first, so nothing piles up.
  • iOS keeps at most 64 pending notifications, so the scheduler caps at 60 and fills them in order of soonest first.
  • Android declares SCHEDULE_EXACT_ALARM and uses a "Class reminders" channel. Android 13+ asks for notification permission the first time a student turns reminders on.
  • On the web, the current in-tab reminder stays as the fallback.

PDF export

On native, the jsPDF output is written to the cache directory with @capacitor/filesystem and handed to the share sheet with @capacitor/share, so it can go to WhatsApp, Drive or Files. On the web it downloads as it does now.

Offline open

After each successful load, the student's own sessions, exams, notices and announcements are cached on the device. With no connection, the app opens on that cache and shows an "offline, last updated …" note.

Shell polish

Android's back button returns to My Timetable before leaving the app. The status bar takes the brand colour, the splash screen hides after the first render, and icons and splash images come from @capacitor/assets.

Feature specs

Search fix

Search is limited to the student's campus. By default it searches only the chosen course, and a toggle widens it to "all courses on this campus" for electives. Each result shows its course name, and the same module code is never listed twice.

Multi-campus

Students pick a campus on the sign-in screen, and it's saved to their record. Admins see only their own campus, and the class, exam and AI import tabs write campus_id automatically. A super admin gets a campus switcher. Faculties and courses are per campus.

Lecturers tab

A lecturer signs in and sees only their assigned module codes. For each code they can move a session for good (day, time, venue), or post a one-off notice: test, cancelled, moved, extra class or note. Students see these notices next to the class in their timetable and in a "Coming up" list.

Announcements tab

Students get an Announcements tab with campus and all-campus posts, pinned first, and expired posts hidden. Admins can create, pin, set an expiry and delete.

Contact footer

A footer gives the maintainer's contact email for queries, plus LinkedIn and Facebook links. The links live in js/config.js, and each one is hidden until its URL is filled in.

Smaller fixes found during review

  • Realtime reloads are debounced so a bulk import causes a single reload.
  • Data loads are filtered by campus, so only that campus's rows are fetched.

Risks & open items

Student records are publicly readable and writable. Students sign in with a student number and no password, so anyone with the anon key can read or change any student's record. That's tolerable for module lists, but app-store privacy reviews will ask about it. A fix means real student sign-in, for example a magic link to the university email. It's outside this plan.
